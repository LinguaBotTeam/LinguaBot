# Обновление базы данных

Команды выполняются из `backend` установленным Python окружения проекта.
URL берётся из `DATABASE_URL` окружения или личного `.env`. Не записывайте
учётные данные в `alembic.ini`, Git или сообщения об ошибках.

Миграции запускаются явно **до старта backend**. Приложение не выполняет
автоматический upgrade или stamp. `create_all()` при запуске приложения
не обновляет структуру существующих таблиц.

## Новая пустая база

```text
.venv/Scripts/python.exe -m alembic upgrade head
```

Затем запускайте backend обычной командой. Сначала миграция, затем сервер:
не создавайте новую установку через запуск приложения перед миграциями.

## Существующая база без Alembic

Остановите backend и сделайте резервную копию. Для SQLite используйте
резервное копирование средствами SQLite или копируйте файл после полного
закрытия подключений; не копируйте только основной файл работающей WAL-базы.
Убедитесь, что выбран правильный DATABASE_URL, не публикуя его значение.

```text
.venv/Scripts/python.exe -m alembic -x legacy_baseline=true stamp 0001_existing_schema
.venv/Scripts/python.exe -m alembic upgrade head
```

Первая команда сначала сверяет структуру четырёх исходных таблиц:
users, dialogues, messages, test_results. Проверяются поля, типы, NULL,
значения по умолчанию, ключи и индексы; содержимое строк не читается.
При отличии команда завершается без отметки версии и изменения данных.
Требуется отдельно выяснить отличие, а не принудительно ставить stamp.
На старой схеме нельзя выполнять `stamp head`: это пропустит обновление.

Если база уже управляется Alembic, достаточно `upgrade head`.
Повторный upgrade не создаёт копии записей.

## Что меняется

Ревизия 0001 описывает прежнюю схему; для существующей базы она только
проверяется и отмечается, её таблицы повторно не создаются. Ревизия 0002
добавляет dialogue_projects и nullable project_id в dialogues. Все старые
диалоги остаются вне проектов. Сообщения, пользователи и assessment сохраняются.

В SQLite новая колонка добавляется без пересоздания dialogues. Внешние
ключи включены на подключении миграции; DDL выполняется в транзакции.
Для миграций проектов требуется SQLite 3.35+. Автономные проверки используют
SQLite; применение на PostgreSQL требует отдельной проверки окружения.
Генерация offline SQL не поддерживается: нужна проверка существующей схемы.
SQLAlchemy может не отражать ON DELETE для inline REFERENCES в SQLite;
поэтому автоматически предложенные изменения FK нужно сверять с
`PRAGMA foreign_key_list(dialogues)`. Проверка миграций сверяет эту связь
непосредственно через PRAGMA и проверяет реальное поведение SET NULL.

Откат до 0001 сохраняет диалоги и сообщения, но **удаляет проекты и их привязки**:
перед ним тоже требуется резервная копия. Откат ниже базовой схемы отключён,
чтобы не удалять исходные таблицы приложения.

Основа: [SQLite ALTER TABLE](https://www.sqlite.org/lang_altertable.html),
[асинхронный Alembic](https://alembic.sqlalchemy.org/en/latest/cookbook.html#using-asyncio-with-alembic).
