# Бэкенд текстового чата

Модуль создаёт личные диалоги, сохраняет сообщения пользователя и ответ заглушки, возвращает историю. Использует общую базу и существующую JWT-авторизацию. Фронтенд чата и подключение ИИ в этот этап не входят.

## Запуск

Из папки `backend`:

```powershell
.\.venv\Scripts\python.exe -m uvicorn linguabot.main:app --app-dir src --reload
```

Новые таблицы `dialogues` и `messages` создаются при старте приложения. Существующие таблицы не изменяются. При настройках по умолчанию данные находятся в `backend/linguabot.db`, если сервер запущен из `backend`.

## Проверка через браузер

1. Открой `http://127.0.0.1:8000/docs`.
2. Зарегистрируй тестового пользователя через `POST /api/v1/auth/register`, если аккаунта ещё нет.
3. Выполни `POST /api/v1/auth/login` с email и паролем. Скопируй `access_token` из ответа.
4. Нажми **Authorize**, вставь токен без префикса `Bearer`, подтверди и закрой окно. Документация сама добавляет заголовок авторизации.
5. В разделе **dialogues** создай диалог через `POST /api/v1/dialogues`:

```json
{"title": "Практика английского", "scenario": "free_chat"}
```

Можно отправить `{}`: название будет `Новый диалог`, сценарий — `free_chat`. В ответе со статусом 201 будет `id` созданного диалога.

6. В `POST /api/v1/dialogues/{dialogue_id}/messages` укажи этот `id` и тело:

```json
{"content": "Hello! How are you?"}
```

Ответ 201 содержит `user_message` и `assistant_message`. Оба сообщения уже сохранены. Заглушка всегда отвечает: «Спасибо за сообщение! Давай продолжим практику.»

7. Вызови `GET /api/v1/dialogues/{dialogue_id}/messages`: в истории появятся сообщение пользователя и ответ. Отправь ещё один текст и загрузи историю снова.
8. Перезапусти сервер и снова запроси историю с действующим токеном — сообщения останутся в базе.
9. Для проверки изоляции создай второй аккаунт, получи его токен и замени токен в **Authorize**. Список второго пользователя не содержит чужие диалоги. Чтение и отправка сообщений в диалог первого пользователя возвращают 404.

## Контракт API

Все четыре операции требуют заголовок `Authorization: Bearer <access_token>`.

| Метод и путь | Тело запроса | Результат |
| --- | --- | --- |
| `POST /api/v1/dialogues` | `title`, `scenario` — необязательные строки | 201, созданный диалог |
| `GET /api/v1/dialogues` | — | 200, список своих диалогов, новые ID сначала |
| `POST /api/v1/dialogues/{dialogue_id}/messages` | `content` | 201, пара `user_message` / `assistant_message` |
| `GET /api/v1/dialogues/{dialogue_id}/messages` | — | 200, сообщения выбранного своего диалога по возрастанию ID |

Диалог в ответе содержит `id`, `title`, `scenario`, `status`, `created_at`, `updated_at`. Статус нового диалога — `active`. В этом этапе операции завершения диалога нет.

Сообщение содержит `id`, `dialogue_id`, `role`, `content`, `correction`, `created_at`. Роль — `user` или `assistant`; `correction` пока равен `null`. Сценарий хранится как метаданные и пока не влияет на фиксированный ответ.

Списки принимают `limit` (от 1 до 100, по умолчанию 100) и `offset` (от 0). Например, для следующей страницы истории: `?limit=100&offset=100`. Пустой список означает, что записей на этой странице нет.

Внешние пробелы строк удаляются. Длина `title` — 1–160 символов, `scenario` — 1–64, `content` — 1–4000. Пустые строки запрещены. Идентификаторы диалогов — целые числа от 1 до 2147483647: этот диапазон совместим с типом Integer в SQLite и PostgreSQL. Неизвестные поля запроса запрещены: владелец определяется по токену, роль сообщения задаёт сервер.

Ошибки используют общий формат проекта:

```json
{"error": {"code": "not_found", "message": "Диалог не найден", "field": null}}
```

- 401: нет действующего токена.
- 404: диалога нет или он принадлежит другому пользователю. Ответ одинаков в обоих случаях.
- 422: неверные поля, пустой текст или недопустимые параметры страницы.

## Устройство модуля

| Файл | Назначение |
| --- | --- |
| `models.py` | Таблицы `Dialogue`, `Message`; связь с существующим пользователем через `user_id` |
| `schemas.py` | Валидация запросов и форматы ответов |
| `repository.py` | SQL-запросы, сортировка и страницы |
| `service.py` | Проверка владельца, заглушка, одна транзакция для пары сообщений |
| `router.py` | Маршруты FastAPI с существующими `CurrentUser` и `SessionDep` |

В общих файлах добавлены только импорт/подключение маршрутов в `api/v1/router.py` и регистрация моделей в `db/session.py`. Логика регистрации и входа сохранена.

Поле `language_id` из архитектурного эскиза отложено до реализации справочника `languages`. Ссылка на отсутствующую таблицу помешала бы запуску приложения.

## Автоматические проверки

Установка уже объявленных тестовых зависимостей:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
```

Из `backend` запусти проверки с отдельной тестовой базой в текущем PowerShell:

```powershell
$previousDatabaseUrl = $env:DATABASE_URL
try {
    $env:DATABASE_URL = 'sqlite+aiosqlite:///./.venv/chat-tests.db'
    .\.venv\Scripts\python.exe -m pytest -o pythonpath=src -q
} finally {
    $env:DATABASE_URL = $previousDatabaseUrl
}
```

Тесты проверяют API, сохранение между сессиями, доступ двух пользователей, валидацию и пагинацию. Отдельная проверка создаёт SQLite-триггер, запрещающий запись ответа: при ошибке откатывается вся пара сообщений и обновление диалога.
